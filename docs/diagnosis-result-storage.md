# 진단 결과 저장 및 재사용

M9 Web/Backend 통합의 첫 작업으로, 완성된 UI 진단 JSON을 기존 스냅샷 SQLite의
`ui_diagnoses` 테이블에 저장한다. 기존 스냅샷은 그대로 보존한다.

## 동작

- 최초 UI 진단 요청은 규칙, 교체 후보, Gemma 설명을 생성한 뒤 전체 결과를 저장한다.
- `GET /api/scans/latest`와 기본 `POST /api/scans`는 저장된 결과를 재사용한다.
  새로고침과 서버 재시작 후에도 설명 및 `generatedAt`이 유지된다.
- 키는 스캔 ID와 정규화된 입력 JSON, `DIAGNOSIS_REVISION`의 SHA-256으로 구분한다.
  같은 ID에 다른 입력이 전달되거나 처리 버전이 바뀌면 새 결과를 생성한다.
- 규칙 기반 대체 설명도 완성된 결과로 저장한다. Gemma 설치 또는 설정 변경 후
  기존 스캔을 다시 설명하려면 명시적으로 재진단한다. 새로운 스캔은 별도로 생성된다.
- 생성 예외는 결과를 저장하지 않는다. 재진단 실패 시 이전 결과는 유지된다.
- 현재 단일 서버 프로세스에서 동일 스캔의 동시 요청을 잠금으로 묶는다.
  여러 서버 프로세스를 운영할 때는 별도의 프로세스 간 생성 잠금이 필요하다.

## 명시적인 재진단

`POST /api/scans`에 `{"refresh": true}`를 전달하면 최신 스냅샷의 결과를 다시 생성한다.
`snapshot`도 함께 전달하면 해당 입력으로 생성한다. UI의 다시 스캔은 기존처럼
실제 데이터를 새로 수집한다. 가격 조회 API는 이 저장 결과에 포함되지 않는다.

규칙, 어댑터, 카탈로그, 프롬프트 변경으로 과거 결과를 자동 갱신해야 할 경우
`backend/app/services/diagnosis_service.py`의 `DIAGNOSIS_REVISION`을 올린다.
기존 `/api/diagnosis/*` 경로의 즉석 분석 동작은 유지한다.

## 검증

`backend/tests/test_diagnosis_cache.py`에서 반복 조회, 실제 별도 Python 프로세스의
SQLite 재사용, 동시 요청, 입력/버전 변경, 명시적 재진단, 실패 시 이전 결과 보존,
UI API의 재사용을 검증한다.
