# 머신러닝 진단

`SpecCheck/backend`의 실제 스냅샷 진단 경로를 규칙 실행에서 학습된 CART 분류 모델 추론으로 변경했다. `SpecCheck-purchase-history` 작업 사본은 변경하지 않았다.

## 적용 범위

- 하드웨어, 소프트웨어, 저장장치, 성능, 신뢰성, 보안의 기존 19개 진단 항목.
- 항목별 모델이 `이상 없음` 또는 `심각도:권장 조치` 클래스를 예측한다. 트리의 분기와 클래스는 scikit-learn이 데이터로 학습한다.
- 기존 `rule_id`는 결과·추천·이력 연결을 위해 식별자로 유지한다.
- 실행 경로는 `diagnose → 특징 추출 → 학습 모델 추론 → 결과/근거 생성`이다. `Rule.evaluate()`는 오프라인 학습에서만 호출한다.
- 구매 후보의 물리적 호환성 제약, 여러 결과의 우선순위 집계, 수집 실패 데이터 제외는 애플리케이션 정책으로 유지한다. 구형 견적 API의 벤치마크 점수 계산과 Agent의 별도 분석 기능은 이번 교체 범위에 포함되지 않는다.
- LLM은 ML 판정 결과의 설명만 작성한다. LLM 장애 시 기본 문구로 설명하고 진단 모델은 그대로 사용한다.

## 데이터와 한계

기존 규칙은 학습용 정답 생성기(weak supervision)로만 사용했다. 현재 저장소의 CPU/GPU 벤치마크는 부품 성능 자료이며, 실제 PC의 고장·수리 결과 정답이 없으므로 고장 정답으로 변환하지 않았다. 기존 테스트 코드는 학습 자료로 사용하지 않았다.

학습 입력은 규칙이 사용하던 측정 항목의 합성 값과 경계 주변 값이다. 날짜는 경과 일수, RAM 클럭은 정격 대비 비율, 이벤트는 건수로 변환한다. 여러 디스크/메모리/GPU는 개별 관측 후 항목별 가장 심각한 결과를 보여준다. 필수 측정값이 없거나 유한한 비음수 수치가 아니면 해당 항목을 판정하지 않는다. 온도가 없는 스로틀링 입력에서는 0을 대체값으로 사용하되 이를 실측 온도 근거로 표시하지 않는다.

공개 데이터는 [Backblaze Drive Stats](https://www.backblaze.com/cloud-storage/resources/hard-drive-test-data)를 이용했다.

- 공식 `data_Q1_2024.zip`의 `2024-01-01.csv` 한 파일만 HTTP Range로 가져왔다.
- 원본 274,660행 중 SMART 5/197이 있는 266,075행에서 고정 시드 reservoir 방식으로 5,000행을 추출했다.
- SMART 5 raw → `reallocated_sectors`, SMART 197 raw → `pending_sectors`.
- 일련번호 등 장치 식별자는 저장하지 않았다. 원본 URL·멤버명·SHA-256·추출 방식은 표본 JSON에 있다.
- 실제 측정 입력을 보완하지만 **이 데이터에도 라벨은 기존 규칙으로 부여했다**. 원본의 `failure`는 당일 디스크 고장 기록이며 PC 전체의 구매·수정 정답이 아니므로 사용하지 않았다.
- 데이터센터 HDD 표본을 개인용 SSD/전체 PC의 실제 고장 확률로 해석하면 안 된다.
- 원출처 요구: Backblaze 출처 표기, 사용 책임 수락, 원본 데이터 자체 판매 금지. 자세한 조건은 원출처 페이지를 따른다.

따라서 이 버전은 **기존 진단 지식을 학습한 초기 모델**이다. 규칙의 오류·편향을 학습할 수 있으며, 기존 규칙보다 정확해졌다고 주장할 근거는 아직 없다. `confidence`는 기존 관측 신뢰도를 계승한 값이고 `model_score`는 트리 잎의 학습 클래스 비율이다. 둘 다 보정된 실제 고장 확률이 아니다.

## 검증

항목별 중복 특징 벡터를 제거한 학습 데이터 합계는 49,333행, 학습 벡터와 겹치지 않는 합성 검증 데이터는 21,238행이다. 항목별 모델용 행의 합계이며 서로 다른 실물 PC 개수가 아니다.

독립 합성 검증 입력이 존재하는 항목에서는 기존 라벨 생성기와의 일치도가 최소 약 99.91%였다. 불리언·작은 정수 범위는 학습에서 가능한 값을 모두 사용했으므로 독립 검증 행이 없고 점수를 `null`로 기록했다. **실제 조치 결과 기반 검증은 수행하지 못했다.** 항목별 클래스 precision/recall/F1과 지원 표본 수는 `backend/app/diagnosis/models/diagnosis-v1.report.json`에서 확인할 수 있다.

JSON 추론 결과와 scikit-learn 예측이 학습/검증 데이터 모두에서 같은지도 학습 스크립트가 검사한다. 회귀 테스트에는 규칙의 `evaluate()`를 호출하면 실패하도록 막은 상태에서도 ML 진단이 작동하는 검사가 포함된다.

## 필요한 추가 자료

실제 정확도를 개선하려면 다음 자료가 필요하다.

1. 비식별화한 정상/문제 PC의 스캔 스냅샷. 문제가 없는 사례도 필요하다.
2. 해당 시점의 증상과 확인된 원인, 전문가가 검토한 진단 항목·심각도·권장 조치.
3. 실제 수행한 설정 변경·드라이버 업데이트·청소·부품 교체 등과 전후 개선 여부.
4. 같은 기기의 여러 스캔을 묶을 비식별 그룹 키와 시간. 학습/평가에 같은 기기가 섞이는 누수를 막기 위해 필요하다.

현재 사용자 스캔을 자동 수집하거나 외부로 전송해 학습하지 않는다. 검토된 자료를 확보하면 별도의 지도학습 파이프라인과 기기/시간별 분리 평가를 추가해야 한다. 현 재학습 명령은 기존 규칙 라벨 기반 초기 모델을 재현하는 용도다.

## 실행과 재학습

학습된 JSON을 저장소에 포함했으므로 기존 서버 실행 방식으로 바로 사용한다. Docker는 기존 `COPY backend/app` 단계에서 모델도 포함한다. 운영 추론은 scikit-learn이나 네트워크가 필요 없다. pickle 모델은 사용하지 않는다.

프로젝트 루트에서 학습 의존성을 설치한다.

```powershell
.venv/Scripts/python.exe -m pip install -r backend/requirements-training.txt
cd backend
# 포함된 공개 표본으로 재학습
../.venv/Scripts/python.exe -m app.scripts.train_diagnosis --external ../datasets/diagnosis/backblaze-smart-sample.json
# 공개 표본을 원출처에서 다시 추출할 경우
../.venv/Scripts/python.exe -m app.scripts.fetch_drive_stats
```

모델 및 리포트는 `backend/app/diagnosis/models/`에 저장된다. 모델 교체 후 서버를 재시작해야 프로세스 내 모델 캐시가 갱신된다. 모델 SHA-256을 진단 이력과 UI 캐시 키에 반영하므로 이전 판정 캐시를 재사용하지 않는다. 모델 누락/계약 불일치는 오류로 처리하며 규칙 판정으로 몰래 돌아가지 않는다.

`GET /api/diagnosis/model`은 알고리즘·학습 라벨 출처·모델 해시를 공개한다. 스냅샷 진단 응답과 UI 응답에도 모델 정보를 포함한다. 이전에 저장된 규칙 기반 진단 이력은 ML 결과로 바꿔 표시하지 않는다.

```powershell
../.venv/Scripts/python.exe -m pytest -q
```

변경 후 백엔드 테스트 314개 및 프런트엔드 `npm run typecheck` 통과. 기존 의존성의 deprecation warning은 남아 있다.
