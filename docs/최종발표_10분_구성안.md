# SpecCheck 최종 발표 구성안

작성 기준: 2026년 11월 9일. 현재 `SpecCheck` 코드와 개정 D07·D08 보고서를 참고했다. PPT 제작 전 내용 구성안이며, 시간에는 화면 시연과 코드 설명이 포함된다. 질의응답은 별도다.

## 발표의 중심 메시지

**SpecCheck는 사용자의 실제 PC 상태를 확인하고, 유지·설정 수정·부품 구매 중 필요한 조치를 제안하는 PC 진단 및 구매 의사결정 지원 시스템이다.**

발표 전체에서 같은 사용자를 따라간다. 사용자가 작업 중 끊김을 경험하고, Agent로 상태를 확인하고, 진단 근거를 읽고, 필요한 부품의 후보와 판매처를 확인하는 순서다. 기술 설명은 각 사용자 행동을 가능하게 한 구현으로 연결한다.

## 2. 슬라이드별 내용과 발표 멘트

### 1장. SpecCheck: PC 진단에서 구매 판단까지

**화면에 넣을 내용**

- 프로젝트명, 팀명, 발표자.
- 부제: 실제 PC 상태에 근거한 관리 및 부품 구매 의사결정 지원.
- 질문: “PC가 느려졌을 때, 어떤 조치가 필요할까요?”

**발표 멘트**

“SpecCheck는 PC가 느려졌을 때 현재 상태를 확인하고, 설정을 바꿀지 부품을 교체할지 판단하도록 돕는 시스템입니다. 한 사용자가 문제를 발견하고 구매 여부를 결정하는 과정을 따라 설명하겠습니다.”

### 2장. 작업 중 끊김을 겪는 사용자의 고민

**사용자 상황: 발표용 가상 사례**

- 사용자가 게임이나 작업을 하면서 브라우저와 여러 프로그램을 함께 실행한다.
- 작업 중 끊김이 발생하지만 원인을 알기 어렵다.
- CPU·GPU 구매를 고려해도 현재 문제를 해결할 부품인지 확신하기 어렵다.

**화면 구성**

사용자의 상황 한 컷과 “설정 문제인가?”, “어떤 부품이 부족한가?”, “지금 구매가 필요한가?”라는 고민을 배치한다.

**발표 멘트**

“예를 들어 게임과 여러 프로그램을 함께 실행할 때 PC가 끊기는 사용자를 생각해 보겠습니다. 이 사용자는 새 부품을 찾아보지만, 어떤 부품이 현재 문제와 관련 있는지 알기 어렵습니다. 저희는 이 판단에 필요한 PC 상태와 진단 근거를 제공하고자 했습니다.”

### 3장. 사용자는 진단 결과를 따라 구매 여부를 결정한다

**시나리오의 순서**

1. 작업 중 끊김을 경험한다.
2. SpecCheck에서 진단을 시작하고 수집 범위를 확인한다.
3. Agent가 PC 사양과 운영 상태를 수집한다.
4. 웹에서 측정값과 진단 근거를 확인한다.
5. 설정·프로그램 조치가 필요한 항목을 먼저 확인한다.
6. 메모리 부족 등 구매 권고 근거가 있는 항목의 교체 후보를 살펴본다.
7. 호환 조건과 판매 정보를 확인하고 외부 판매처로 이동한다.

**분기 설명**

- 확보된 정보에서 조치할 이상 징후가 없으면 현재 유지.
- 전원 계획이나 실행 프로그램 문제라면 설정·소프트웨어 수정.
- 메모리 부족이나 저장장치 이상 등 해당 규칙에 걸리면 구매 검토.

**발표 멘트**

“사용자는 진단을 시작한 뒤 측정값과 권고 이유를 확인합니다. 설정 변경으로 해결할 항목과 교체를 검토할 항목을 구분해서 보여주고, 구매 권고 항목에는 교체 후보와 판매처를 연결합니다. 오늘은 이 중 메모리 부족으로 구매 검토까지 이어지는 사례를 중심으로 설명하겠습니다.”

**구현과 시나리오의 경계**

프로그램 정리 후 다시 측정하는 행동은 사용자가 수행하는 시나리오다. 현재 시스템이 수정 조치를 자동 수행하거나, 재측정 결과를 전후 개선폭으로 자동 비교한다고 설명하지 않는다. 구매 규칙과 수정 규칙이 함께 발생하면 현재 종합 판정은 구매가 될 수 있다. 수정 완료를 확인한 뒤에만 구매를 허용하는 절차는 구현되어 있지 않다.

### 4장. Agent가 사용자 PC의 실제 상태를 수집한다

**핵심 설명**

Agent는 사용자 Windows PC에서 실행되는 수집 프로그램이다. 일반 웹 화면에서 직접 얻기 어려운 PC 사양·성능·시스템 이벤트를 Windows 조회 기능으로 읽어 진단 입력을 만든다.

**화면에 넣을 기능**

| 기능 | 수집·처리 내용 | 사용자에게 주는 정보 |
| --- | --- | --- |
| 하드웨어 수집 | CPU, GPU, RAM, 저장장치, 메인보드, OS | 현재 장착한 부품과 사양 |
| 성능 수집 | CPU·메모리·디스크 부하, 상위 점유 프로세스 등 | 측정 구간의 자원 사용 상태 |
| 저장장치 건강도 | 여유 공간, 지원되는 SMART·수명 정보 | 저장장치 점검에 필요한 신호 |
| 신뢰성 이벤트 | WHEA, 비정상 종료, 블루스크린·디스크 오류 집계 | 최근 오류 발생 이력 |
| 선택적 보안 수집 | 별도 동의·지원 환경에서 Sysmon 이벤트 | 프로세스 이벤트 분석 자료 |
| 기록과 전송 | 표준 스냅샷, 로컬 SQLite, 선택 업로드 | 수집 결과 보존과 웹 조회 연결 |

**보여줄 화면**

로컬 Basic Scan의 권한 승인, PC 정보 수집, 로컬 저장, 서버 전송, 진단 결과 단계를 보여준다. 수집 시각, 수집 출처, 실패·결측 상태도 한 곳 강조한다.

**발표 멘트**

“Agent는 사용자 PC에서 정보를 수집하는 역할입니다. 부품명뿐 아니라 실제 자원 사용 상태와 오류 이력을 함께 확인합니다. 권한이나 장치 지원 문제로 읽지 못한 값은 미확인 상태로 남깁니다. 이를 통해 서버가 어떤 자료를 근거로 판단했는지 사용자가 확인할 수 있습니다.”

**사용 방식 구분**

- 본 발표의 주 시연은 로컬 Basic Scan으로 통일한다. 로컬 실행기로 서버와 UI를 실행한 후 진단 버튼으로 Agent를 시작한다.
- 공개 모니터링 연결은 별도 사용 방식이다. Windows GUI에서 웹의 8자리 연결 코드를 입력하고 수집·전송에 동의하면 반복 전송과 웹 이력 조회를 이용한다.
- 공개 모니터링의 전송 범위는 하드웨어·성능·선택적 보안이다. 로컬 Basic Scan의 저장장치 건강도·신뢰성 전체 수집 범위를 그대로 공개 서버에 전송한다고 설명하지 않는다.

### 5장. 서버가 수집 근거로 필요한 조치를 구분한다

**화면에 넣을 내용**

- FastAPI 서버가 스냅샷의 데이터 형식을 검증한다.
- 현재 6개 규칙 모듈, 19개 규칙으로 확보된 자료를 평가한다.
- 결과에는 문제, 심각도, 측정 근거, 권고 조치가 포함된다.
- 종합 결과는 유지·설정/소프트웨어 수정·구매 검토로 구분한다.

**같은 증상에서 다른 조치가 나오는 예**

| 확보한 근거 | 해당 규칙의 권고 |
| --- | --- |
| 전원 계획이 절전 모드로 확인됨 | 설정 수정 |
| 측정 구간에서 CPU 부하가 높게 유지되고 점유 프로세스가 확인됨 | 실행 프로그램 확인·정리 |
| 평균 커밋 비율 90% 이상과 가용 메모리 평균 1,500MB 이하가 함께 관측됨 | 메모리 증설 검토 |
| 수집된 자료에서 조치가 필요한 항목을 찾지 못함 | 현재 유지 |

**발표 멘트**

“같이 느리다는 증상이어도 확인한 근거에 따라 조치가 달라집니다. 전원 계획 문제에는 설정 변경을 안내하고, 메모리 부족 신호가 함께 나타나면 증설을 검토하도록 합니다. 예를 들어 메모리 규칙은 평균 커밋 비율과 가용 메모리를 함께 확인합니다. 이 기준은 구현된 규칙이며, 진단 정확도를 입증한 임상적 기준처럼 제시하지 않습니다.”

**표현상 주의**

측정은 짧은 표본일 수 있다. 한 번의 검사로 고장이나 원인을 확정한다고 말하지 않는다. 커밋 비율·가용 메모리는 메모리 압박의 신호이며, 두 조건만으로 실제 페이징 원인을 확증했다고 설명하지 않는다.

### 6장. 구매가 필요한 문제를 교체 후보로 연결한다

**주 시나리오의 계속**

메모리 부족 권고를 받은 사용자가 자신의 플랫폼에 맞는 메모리 후보를 확인한다.

**화면에 넣을 내용**

- 구매 권고가 발생한 진단 항목에서 교체 후보를 만든다.
- 실제 제품 카탈로그에서 후보를 고른다.
- 메모리 세대, CPU 소켓, 저장장치 인터페이스 등 확인 가능한 조건을 검사한다.
- 빈 슬롯, 물리 규격, 실제 장착 조건 등이 불명확하면 추가 확인 사항으로 표시한다.
- 선택적으로 Ollama/Gemma가 진단 설명과 주어진 카탈로그 후보의 선택 이유를 작성한다.

**발표 멘트**

“사용자는 메모리가 부족하다는 안내에서 멈추지 않고 교체 후보를 확인할 수 있습니다. 수집된 PC 사양과 제품 카탈로그를 바탕으로 조건을 비교하고, 확인하지 못한 장착 조건도 함께 보여줍니다. Gemma가 연결된 경우에는 주어진 후보 안에서 선택 이유를 설명합니다. 모델을 사용할 수 없으면 기본 안내를 제공합니다.”

**AI 역할의 정확한 설명**

유지·수정·구매 판정은 규칙 엔진이 담당한다. 로컬 진단 UI 경로의 Gemma는 확정된 진단과 제한된 후보를 바탕으로 설명·후보 선택을 보조한다. 공개 모니터링 저장 경로에서 Gemma 설명을 자동 생성하지는 않는다. 호환성 점수는 프로그램 내부 기준이며 장착 성공 확률이 아니다.

### 7장. 사용자가 판매 조건을 확인하고 구매처로 이동한다

**화면에 넣을 내용**

- 후보 부품별 판매 상품과 출처.
- 확인된 상품 가격, 한국 배송비, 합계, 조회 시각.
- 같은 부품·같은 통화이며 비교 조건을 충족하는 조회 상품 간 가격 비교.
- 외부 판매처 또는 검색 링크로 이동.
- 선택적으로 구매 후 사용자가 직접 입력한 구매이력을 저장하고 공개 여부를 관리.

**발표 멘트**

“교체 후보를 정한 사용자는 판매 정보를 확인하고 판매처로 이동합니다. 가격뿐 아니라 배송비와 조회 시각을 함께 표시하고, 확인되지 않은 값은 미확인으로 남깁니다. 현재 시스템은 외부 판매처로 구매 경로를 연결합니다. 구매이력은 사용자가 직접 입력하는 방식이며, 판매처의 결제 완료를 자동 확인하는 기능과는 구분합니다.”

**시연 범위**

판매처로 이동하는 지점까지 보여준다. 실제 결제는 서비스의 구현 범위가 아니다. 실상품 인증 응답을 확보하지 못한 환경에서는 가격 미확인 상태를 그대로 보여주거나, 시험용 화면이라는 표시와 함께 검증용 데이터를 사용한다. 진단 예시값·가격 예시값을 실제 측정·실제 판매가로 소개하지 않는다.

| 위치 | 구성 | 책임 |
| --- | --- | --- |
| 사용자 PC | Python Agent, PowerShell CIM/WMI·이벤트 조회, SQLite | 수집·표준화·로컬 기록·선택 전송 |
| 서버 | FastAPI, 데이터 검증, 규칙 엔진, 진단 서비스 | 입력 검증·판정·기록·응답 |
| 웹 | React/TypeScript 진단 UI, 별도 모니터링·견적 웹 | 진행 상태·근거·교체 후보·판매처 표시 |
| 선택 서비스 | Ollama/Gemma, eBay 상품·가격 연동 | 설명·후보 선택 보조, 판매 정보 조회 |

**아키텍처 그림에 붙일 데이터 이름**

1. Agent에서 서버로 보내는 자료: 버전·수집 시각·기기 식별자·수집 상태가 있는 스냅샷.
2. 서버에서 웹으로 보내는 자료: 진단 항목·근거·권고 조치·후보.
3. 웹에서 사용자가 선택하는 다음 행동: 관리 조치 확인 또는 판매처 이동.

**발표 멘트**

“Agent와 서버는 서로 다른 실행 단위입니다. Agent는 Windows에 접근해 자료를 수집하고, 서버는 표준 입력을 검증한 뒤 규칙을 적용합니다. 웹은 결과와 근거를 사용자가 이해할 수 있게 표시합니다. 저장소도 로컬 Agent와 개발 서버에서는 SQLite를 사용하고, 공개 모니터링에는 PostgreSQL 연결을 지원합니다.”

**공개 운영에서 어필할 구현**

기기별 조회키와 전송키 분리, 동의 기반 전송, 연결 해제 시 이력·키 삭제를 보조 문구로 넣는다. 로컬 모드는 PC 내부에서 실행할 수 있고 공개 모니터링은 동의한 정보를 서버로 전송하므로, 전체 서비스에 대해 “모든 정보가 PC 밖으로 나가지 않는다”고 설명하지 않는다.

### 9장. 핵심 코드는 측정값을 진단과 추천으로 연결한다

**화면 구성**

전체 파일이나 IDE 화면을 작게 넣기보다 아래 실제 호출 중 네 줄을 크게 보여주고, 오른쪽에 각 줄의 입력·출력을 짧게 설명한다. 아래는 `diagnose_for_ui()`의 핵심 호출을 발췌한 것으로 독립 실행 예제는 아니다.

```python
result = diagnose(snapshot)
recommendations = build_recommendations(snapshot, result, catalog)
ai, recommendations = explain_for_ui_bundle(result, recommendations)
diagnosis = to_ui_diagnosis(snapshot, result, ai, recommendations)
```

- `diagnose`: 확보된 자료에 규칙을 적용해 판정과 근거 생성.
- `build_recommendations`: 구매 권고 진단을 제품 후보로 연결.
- `explain_for_ui_bundle`: 선택적 모델 설명·후보 선택, 실패 시 기본 안내.
- `to_ui_diagnosis`: 웹 표시 형식으로 변환.

원본 함수에는 가격 상태 조회·보강, 캐시 키 계산, 잠금, 결과 저장도 포함된다.

**발표 멘트**

“이 네 호출이 사용자 흐름을 코드로 연결하는 부분입니다. 같은 스냅샷을 규칙 엔진에 넣고, 구매 권고 항목에서 제품 후보를 만들고, 설명을 붙여 웹 응답으로 변환합니다. 모델을 사용할 수 없어도 규칙 판정과 기본 안내는 유지됩니다. 수집기와 규칙을 모듈로 분리해 새로운 항목을 추가할 수 있도록 구성했습니다.”

**교체 가능한 코드 예시: 메모리 규칙**

발표가 기술 심사 중심이라면 위 호출부 대신 다음 조건을 보여준다. `MemoryPressure.evaluate()` 발췌다.

```python
committed = _stat(data, "memory.committed_percent", "avg")
available = _stat(data, "memory.available_mb", "avg")
if committed is None or available is None:
    return None
if committed < MEMORY_COMMITTED_HIGH or available > MEMORY_AVAILABLE_LOW_MB:
    return None
```

현재 상수는 각각 90.0과 1500.0이다. “두 지표를 함께 보고, 값이 없으면 이 규칙으로 판정하지 않는다”는 구현 원칙을 설명한다. 두 코드 예시를 모두 자세히 설명하면 시간이 초과되므로 하나를 본문에, 나머지를 부록에 둔다.

### 10장. 핵심 흐름 구현과 검증 결과

**화면에 넣을 내용**

- 구현: 실제 PC 수집·로컬 저장·진단·교체 후보·판매처 연결.
- 최신 D07·D08 기록: 자동화 검증 참고 합계 503건 통과.
- D07 등록 사례 36건: 통과 32건, 환경 차단 4건.
- 후속 과제: 외부 연동 실환경 재검증, 조치 전후 비교와 구매 후 자동 검증.

**발표 멘트**

“PC 상태 수집에서 진단 근거와 구매처 연결까지의 핵심 흐름을 구현했습니다. 최신 보고서에는 자동화 검증 503건 통과와 D07 등록 사례 32건 통과, 4건 환경 차단을 기록했습니다. 남은 실환경 검증과 조치 전후 비교를 보완해 사용자가 구매 여부를 판단할 근거를 더 충실히 제공하겠습니다.”

**수치 설명 메모**

503건은 서로 다른 시험 계층을 합한 참고 수치다. D07의 36건과 합산하지 않는다. 진단 정확도·사용자 만족도·비용 절감률을 의미하지 않는다. 이번 발표 구성 작업에서는 시험을 재실행하지 않았으며 기존 검증 기록을 인용했다. 전체 시스템 최종 인수는 보류된 상태다.

## 3. Agent와 서버를 어필할 때 사용할 설명

**Agent 설명 문장**

“SpecCheck Agent는 사용자 PC에서 사양과 운영 상태를 수집하고, 수집 상태까지 포함한 표준 스냅샷으로 기록하는 Windows 프로그램입니다. 이 기록이 진단 근거가 되고, 지원되는 이력 분석의 입력으로도 사용됩니다.”

**서버 설명 문장**

“서버는 Agent가 보낸 자료를 검증하고, 확보된 근거에 규칙을 적용해 필요한 조치를 구분합니다. 웹에서 진단 결과와 그 결과에 연결된 부품 후보를 조회하도록 제공합니다.”

| 어필할 부분 | 코드·설계에서 확인한 특징 | 사용자에게 설명할 의미 |
| --- | --- | --- |
| 실측 입력 | Windows 하드웨어·성능·이벤트 수집 | 사용자의 현재 PC 상태를 판단 자료로 활용 |
| 결측과 실패 처리 | 섹션별 상태, 수집 예외 격리, 결측 보존 | 읽지 못한 자료를 정상 수치로 오해하지 않도록 표시 |
| 설명 가능한 판정 | 규칙 코드, 근거, 조치, 수집 출처 | 구매 권고가 나온 이유 확인 |
| 수집 확장 구조 | Collector 상속·등록, 표준 스냅샷 | 수집기별 책임 분리와 추가 확장 |
| 동의와 접근 관리 | 공개 경로의 동의, 전송키/조회키, 삭제 | 수집·전송·조회 범위를 관리 |
| 이력 분석 | 로컬 상관 후보, 기기별 z-score, 선형 추세 | 단일 검사 외 변화 정보를 보조적으로 확인 |
| 모델 장애 대응 | Ollama 미사용·실패 시 템플릿 | 모델 연결 상태와 별개로 기본 진단 제공 |

상관 후보는 원인 확정이나 악성코드 확정이 아니다. z-score 신호가 자동으로 구매 판정을 만들지는 않는다. 선형 추세의 임계 도달 예상일은 실제 고장일 예측이 아니다. 표본과 관측 기간이 부족하면 분석을 보류한다. 이력 분석 세부는 부록·질의응답에 배치하면 주 시나리오를 유지하기 쉽다.

## 5. 부록에 둘 내용

- 견적 평가: CPU/GPU 성능 데이터, 간이 호환성, 위험도·가격 평가.
- 별도 Canvas 기반 PC 조립 시각화: 부품 장착·해제 순서 제약.
- 구매이력: 사용자 직접 입력, 본인 기록과 공개 동의 기록 구분.
- 고급 분석: 이벤트 상관 후보·이상 신호·선형 추세의 조건과 한계.
- 공개 모니터링: 연결 코드·키 분리·보관·삭제·재전송.
- 검증 상세: Agent 125, Backend 295, PostgreSQL 별도 파라미터 15, UI 로직 53, Edge 15.

위 기능들은 전체 프로젝트 설명에 포함하되, 본문에서는 주 시나리오와 연결되는 부분에만 시간을 사용한다. 3D 조립 화면이 진단·구매 흐름에 자동 통합되었다고 설명하지 않는다.
