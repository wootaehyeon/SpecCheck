미검토 케이스는 0건이다. 수행 완료는 32/36건(88.9%), 시스템 시나리오는 10/14건(71.4%)이다. B 4건은 선행 조건 확인과 가능한 하위 시험을 수행했으나 원래 시나리오 전체를 완료하지 못했다. 이를 ‘미수행 0’이나 ‘전체 합격’으로 표기하지 않는다.

# 1. 프로젝트 개요

## 1.1 시스템 명

SpecCheck: PC 상태 진단 및 구매 의사결정 지원 시스템.

## 1.2 시스템 개요

Windows Agent는 하드웨어·성능·저장장치 상태·신뢰성·선택적 보안 정보를 수집하고 로컬 SQLite에 저장한다. Backend는 수집 상태와 근거를 확인해 유지·설정 수정·구매를 구분한다. 공개 모니터링은 읽기키·전송키를 분리하고 hardware/performance/security만 받는다. 로컬 Basic Scan의 수집 범위와 구별한다.

견적 화면은 평가 API의 등록 벤치마크 점수·호환성 결과를 사용한다. 현재 PC의 실측 성능과 구별하며, 미등록 모델·가격 조회 실패를 예시 수치로 대체하지 않는다. 구매 경로는 후보·판매 조건과 외부 판매 링크를 제공하며 결제는 외부 판매처에서 진행한다.

# 2. 테스트 개요

## 2.1 범위와 판정 기준

기존 D07의 STC 14건과 ATC 22건 모두를 검토했다. 각 케이스는 아래에서 입력·기대값·실제 결과·근거·판정을 연결한다. P는 예상과 일치한 수행 완료, F는 예상 불일치, B는 선행 환경 차단, NT는 착수하지 않은 케이스다. 이번 상태는 P32/B4/F0/NT0이지만 B를 수행 완료나 합격으로 합산하지 않는다.

실제 수집의 partial은 온도·관리자 SMART·Sysmon 정보를 확보했다는 뜻이 아니다. 결측과 접근 거부를 성공 수치로 바꾸지 않았다. 규칙 발동을 실고장 또는 진단 정확도 입증으로 해석하지 않는다.

# 5. 테스트 환경

## 5.1 구성

Windows11 호스트에서 Python3.12.6, pytest8.2.0, Node24.14.0, Playwright1.56.1 및 설치된 Microsoft Edge를 사용했다. API는 FastAPI/Uvicorn, 저장은 격리 SQLite와 Docker PostgreSQL17이다. 상세 실제 버전·권한·소스 해시는 environment.json과 source-manifest.json을 따른다.

실환경 HTTP 서버는127.0.0.1:8052, PostgreSQL은127.0.0.1:55433에만 바인딩했다. 브라우저 회귀는127.0.0.1:8051의 별도 서버·SQLite를 사용했다. 합성 상품 응답과 실수집 데이터를 각 케이스에 명시했다. 실제 키·DB 암호를 보고서에 넣지 않는다. 공개 Render 서버의 이번 읽기 전용 확인에서도 인증서 검증을 켠 HTTPS health200, 모니터링 enabled/persistent=true, 개발API·.env·.git/config404를 확인했다(public-probe.json). 운영 재시작 검증을 대신하지 않는다.

## 5.2 반복 전송 기준과 측정 한계

STC-REAL-014는 목표가 비어 있던 케이스에 대해 검증자가 실행 전에 10대·30초 간격·10분, 오류/누락/중복0, 업로드 p95≤2초·최대≤5초의 로컬 기준을 정했다. 이는 팀이 승인한 운영 SLA가 아니다. 21라운드의 시각과 최대 응답시간은 runtime.json의 timeline에 보존했다.

측정한 응답시간은 첫 업로드 HTTP 왕복이다. 동일 ID 재전송·최신 조회·이력 개수 확인을 매 라운드 수행하고 중간에 Backend와 DB를 재시작했다. DB 크기는 종료 시 절대 크기이며 샘플당 성장률이나 최대 수용량으로 해석하지 않는다. 24시간·실제10대 물리 PC·외부 네트워크·모바일 전체 조합은 확인한 범위 밖이다.

## 7.2 증빙 파일과 재현

이번 직접 근거는 outputs/reports/evidence/d07-final-20261109/에 있다. case-results.json은36건 입력·기대·실제·판정과30건 백로그 대조를 담고, 자동화시험목록.md는503개 개별 항목을 담는다. 원래204건 로그와 기존 실환경/HTTPS 증빙은 상위evidence 폴더에 보존한다. HML 제출본과 최신 Markdown은 같은 판정 데이터를 사용한다.

Python 시험은agent/backend 각 작업폴더에서 .deployment-tmp/venv-py312/Scripts/python.exe -X utf8 -m pytest tests -q로 재현한다. Backend는TELEMETRY_API_ENABLED=true, MONITOR_TEST_DATABASE_URL 비움, LLM_ENABLED=false를 지정한다. PostgreSQL 파라미터는 격리DB를 지정해 -k postgres로 선택한다.

UI 로직: npm run test:ui. 정적 검사: npm run lint, npm run typecheck. 브라우저: frontend/tests에서SPECCHECK_TEST_PYTHON을 같은Python 절대경로, MONITOR_TEST_BROWSER=msedge, SPECCHECK_TEST_PORT=8051로 지정하고Playwright를 실행한다. 실행별 새 증빙 경로를 사용한다.

실수집·격리PostgreSQL·10분 반복 시험은run_real_checks.py로 재현한다. 실행 전 임시 컨테이너 이름과 포트의 충돌 여부를 확인한다. finalize_report.py는최종 로그를 검증하고 판정표·Markdown·HML·증빙ZIP을 생성한다. 사람의 인수 서명은 생성하지 않는다.
